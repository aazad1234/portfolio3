Web development practices I keep coming back to

A short list of habits that make front-end work more resilient: semantic HTML, honest states, fewer dependencies, and accessibility as a definition of done.

Start with semantic HTML

Before the component library, the state manager, or the animation layer, there is a document. Buttons should be buttons. Links should go somewhere. Headings should describe the structure of the page, not the size of the text. Forms should have labels.

Semantic HTML is not a nostalgic preference. It is the cheapest accessibility win available, and it gives browsers, search engines, and assistive technology a reliable model of the page. A surprising number of complex front-end bugs disappear when the underlying elements are correct.

Design the states, not just the screen

A screen is a snapshot. A product is a set of transitions: loading, empty, partial, error, success, offline, and everything in between. The polished mockup is usually the least common state in real use.

I try to design the loading and error states at the same time as the happy path. What does the page look like before the data arrives? What does a failed request say? Can the person retry without losing their place? These decisions are part of the interface, not an implementation detail.

Treat performance as a design constraint

Performance is not only a back-end concern. Image choices, font loading, third-party scripts, and animation decisions all shape how a page feels. A layout that requires a large image to make sense is a fragile layout.

I set a simple budget early: a target page weight, a maximum number of font families, and a rule that noncritical scripts load after the content. The budget creates useful conversations. It also prevents a small design decision from quietly becoming a large performance problem.

Use fewer dependencies

Libraries are not free. Every dependency adds install time, upgrade work, security surface, and a new vocabulary for the next person. Sometimes that trade is worth it. Sometimes a small utility function would have been enough.

A useful question is: what happens if this dependency disappears? If the answer is a week of work, the abstraction needs to be understood and documented. If the answer is an afternoon, it may still be fine, but it should be a conscious choice.

Make accessibility part of done

Accessibility is easiest when it is not a separate phase. Use landmarks and headings from the start. Check keyboard order as you build. Test focus states with the real design. Write error messages that explain how to recover. Run automated checks, then do the manual checks automation cannot do.

The goal is not a perfect score. The goal is a page that more people can use, including people who are tired, distracted, on a slow connection, or using a keyboard because a trackpad is not available.

Key takeaways

  • Correct elements are cheaper than clever workarounds.
  • Design loading, empty, and error states alongside the happy path.
  • Set a performance budget before the first component is built.
  • Treat accessibility as part of the definition of done.
